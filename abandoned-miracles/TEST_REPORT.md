### Why nothing was run in the game

* The only way to run Bedrock in this environment is Bedrock Dedicated Server through Minecraft Creator Tools. That requires accepting the Minecraft End User License Agreement, which the project owner must do personally (`npx -y @minecraft/creator-tools@0.21.0 eula`); it was not accepted on their behalf.
* No Minecraft client exists here, so nothing visual or audible could be observed in any case.
* Consequently **no screenshot in this repository is from the game.** Images under `docs/previews/` are produced by the project's own software renderer from the shipped geometry, textures and animation data.

### First things to check in a real game

1. Import the `.mcaddon`, enable both packs on a world, watch the Content Log while it loads.
2. `/abm:summon vesperra` on flat ground: model, textures, idle and walk; boss bar; action-bar line.
3. Does the boss walk and turn smoothly? If it jitters or does not move, switch *Stepwise boss movement* on in the Codex and report it.
4. Are floor telegraphs visible, flat on the ground and aligned with where damage lands? (`/abm:debug attack 1` … `7`)
5. `/abm:debug phase2` and `/abm:debug kill`: transformation and death sequences.
6. Damage taken in enchanted diamond versus the numbers in DESIGN_SPEC §3.5.
7. The same on a phone, watching frame rate during each boss's ultimate.

## 3. Simulation

`node tools/sim/run.mjs` loads the **shipped** `scripts/main.js` against a strict stand-in for the Script API (`tools/sim/mock-server.mjs`) and plays whole encounters with bots. The stand-in is deliberately unforgiving about everything that can be checked against the real pack files: entity identifiers, property names, types and ranges, entity events, particle identifiers and the Molang variables each particle reads, sound events, items, structures and loot tables must all exist; world-changing calls inside a before-event throw, as in the game; any attempt to modify a block fails the run.

It is a model, not Minecraft: it cannot show that the engine behaves as the model assumes (movement physics, event ordering, invulnerability frames, armour arithmetic).

## 6. Performance

Not measured on any device. What was done instead:

* **Budgets enforced by the validator**: ≤ 480 cubes and ≤ 120 bones per model, textures ≤ 512², steady particle emitters ≤ 600 particles, audio ≤ 12 MB, mono clips.
* **No per-tick world scans**: participants come from one bounded player query per encounter every 5 ticks; orphan sweeps run every 10 s on tagged entities only; arena scans happen once per summon.
* **Bounded state**: one timeline per encounter; helper entities capped at 12 per encounter; all per-player data cleared on leave and at encounter end.
* **Counts observed in the simulated solo fights** (script calls, not rendered particles — one call may draw a whole line or arc on the client):

| Boss | Peak particle calls in one tick | Total particle calls | Peak live entities (boss + helpers) |
|---|---:|---:|---:|
| Vesperra | 41 | 2,271 | 7 |
| Cantor XIII | 72 | 11,148 | 3 |
| Nomos | 78 | 5,087 | 1 |
| Orison | 51 | 2,285 | 5 |

Risks to watch on low-end phones: the ultimates draw the most telegraph geometry at once; the *Reduced decorative particles* setting halves decoration but (by design) not telegraphs.

## 7. Known issues and limitations

* Nothing has been run in Minecraft. Any of the assumptions the simulation makes about the engine could be wrong; the most consequential are script-driven movement (velocity impulses and `setRotation` on a mob without AI goals), the timing of `beforeEvents.entityHurt` relative to invulnerability frames, and flat-on-floor particle rendering.
* Player absorption hearts are bypassed by hazard damage (the Script API does not expose them).
* Hazards assume a level arena floor. On uneven ground telegraphs are drawn at the summoning height and may sink into or float above terrain.
* Health scaling for multiple players follows the brief's formula, but Bedrock's half-second hurt immunity means several players do not add damage linearly; four-player fights may run long until tuned with real players.
* Blockbench `.bbmodel` files are generated to Blockbench's project format but have not been opened in Blockbench here.
* The test world builds its arenas with commands during the first seconds after it is opened; this has not been observed in game.
* Minecraft Creator Tools' `export world` command rewrites pack manifests in place. It is not used by the build; do not run it against `packs/`.
* **First real play session reported "a lot of errors"; the messages themselves were not available.** The build was therefore audited against Mojang's vanilla packs and the Script API documentation instead, and these real defects were found and fixed: three helper entities used a render controller that names a material they did not declare (an error for every frame they are drawn); three helper animation controllers left their first state on a query that is always 0 there, so they never left it; Seals, Codex and trophies listened only to the block-interaction event that fires when the block itself reacts, so tapping a plain floor did nothing; the packs asked for the newest script module (game 1.26.60) although 1.26.10 has everything they use; bosses carried the `monster` family, which the game removes on Peaceful; the test world was in Creative, where the bosses cannot hurt anyone; a failure inside a per-tick path was logged twenty times a second. Whether these were the errors that were seen is not known.
* **Fight length sits at the low end of the target.** The simulated bot never gets hit, never loses a swing and finishes each fight in about four minutes; that is the floor, not the expectation. Real players will take longer. If real fights run long, raise a boss's `damageTaken` in `src/config.ts`.
* **The bot does not model Slowness or knockback.** Nomos' wet ink and Orison's hourglasses slow players, and most hits knock the player back; the "avoidable at walking speed" proof covers each hazard from a clean start, not escaping the next one while slowed or displaced. These combinations need a human check.
* **Particle peaks.** Nomos' chessboard telegraph (The Great Recalculation) and Cantor's wave rings reach roughly 75 particle spawn calls in one tick in simulation. Each call is a single emitter with a bounded lifetime, but the cost on low-end phones is unmeasured. `vfx.density` does not reduce telegraphs by design.
* **Animation blending is authored blind.** Poses and timings were checked frame by frame in the project's own renderer, which evaluates the same Molang; the game's animation-controller blending between states has not been observed.
* **Scripted locomotion has not been felt in game.** Bosses are moved by impulses every tick. If a boss stutters or slides on a real device, turn on "Stepwise boss movement (fallback)" in the Codex and report it.
